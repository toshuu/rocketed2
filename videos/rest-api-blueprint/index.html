First: what is an API?

A messenger between two pieces of software.

An API defines how software asks for data or actions—and how the other side replies.

Meet the resource

Everything starts with a thing.

A user. A product. An order. APIs expose these as resources, usually at URLs called endpoints.

/users · /products · /orders
Resources are the nouns04 / 15

The URL tells you where

An endpoint points to a resource.

GET https://api.shop.com/products/42

The URL identifies the destination and often the exact resource you want.

Endpoint = address for a resource05 / 15

HTTP methods tell you what to do

Same resource. Different action.

1GET — read a product
2POST — create an order
3PUT / PATCH — replace or update
4DELETE — remove a resource
GET should retrieve data. POST commonly creates. PUT replaces; PATCH updates part. DELETE removes.
Method = intended action06 / 15

Let's send a request

The client asks for product 42.

GET /products/42 HTTP/1.1
Host: api.shop.com
Accept: application/json

The request contains a method, a URL, headers, and sometimes a body.

Step 1 · Request07 / 15

The server does the work

It checks, finds, and prepares.

The server can check access, run business logic, read a database, and prepare a result.

Status codes are quick signals

Did it work?

200 OKRequest succeeded.
201 CreatedA new resource was created.
400 Bad RequestThe request is invalid.
401 / 403Not authenticated / not allowed.
404 Not FoundThat resource does not exist here.
500 Server ErrorThe server failed unexpectedly.
The status code tells you the outcome. The response body may explain more.
Know the signal, then inspect the details10 / 15

Where JSON fits

JSON is a common format for the data.

{ "name": "Blue Mug", "price": 12.99 }

The server sends text in a known structure. The app parses it into data it can use.

Format = how data is packaged11 / 15

Not every request has a body

Read vs. write requests.

A POST request often includes JSON to create something. GET usually asks for data without changing it.
Request shape depends on the method12 / 15

A real-world flow

Placing an online order.

1App sends POST /orders with cart details.
2Server checks the user and stock.
3Server saves the order.
4Response returns 201 Created and an order ID.
One familiar app action, several steps13 / 15

Three things to get right

Build APIs that are safe and predictable.

✓Authentication: who are you?
✓Authorization: may you do this?
✓Validation: is the input acceptable?
✓HTTPS: protect data in transit.
✓Errors: return useful, consistent responses.
Correctness includes security14 / 15
